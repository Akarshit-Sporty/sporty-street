# Sporty Street backend

Backend MVP: five-player fantasy squad, one delayed substitution, live scoring, round results,
reward points and a gift shop. One Java 21 / Spring Boot 4 app and PostgreSQL 16.
Read-only social preview APIs supply leagues, rivalries, Banter and manager discovery.

## Start

Docker with Compose is sufficient; no host Java, Maven, PostgreSQL, curl or jq is needed for the demo.

```sh
docker compose up --build
```

- API: http://localhost:8080/api/v1
- Swagger UI: http://localhost:8080/swagger-ui.html
- OpenAPI: http://localhost:8080/v3/api-docs
- Health: http://localhost:8080/actuator/health

Optional settings: copy `.env.example` to `.env`. Default Compose enables the `local` demo
profile: mock users, scripted fixtures and local controls. It is not production authentication.
PostgreSQL stays private to the Compose network. Its named volume preserves data on restart.

## Football catalogue and player photos

The seed contains 60 recognizable players from Real Madrid, FC Barcelona, Manchester City,
Liverpool, Bayern Munich and Paris Saint-Germain. Names, positions, national teams and club
affiliations use a **2024/25 season snapshot**, not a current transfer feed. Source links and the
editable roster are in `src/main/resources/seed/football-2024-25.json`.
The rounds are **European Superstars** and **Champions Night**. Fixtures, schedules, match events,
scores and rankings are generated by the simulator; they are not real match results.

Every player's `imageUrl` is a same-origin path such as `/media/players/kylian-mbappe.jpg`.
Resolve it against the API origin: `http://localhost:8080/media/players/kylian-mbappe.jpg`.
These are actual player photographs bundled under `src/main/resources/static/media/players`
inside the application JAR/Docker image. GET/HEAD is public so `<img>` needs no auth header.
No image CDN, download on startup, extra container or image volume is required.
If the frontend uses a separate origin, resolve URLs against the backend or proxy `/media` too.

Wikimedia Commons attribution, source pages and per-image licences are available at
`/media/players/credits.json`; retain these credits when reusing the photos. The optional
`python3 scripts/fetch-player-images.py` refreshes assets from Wikimedia and requires network
access; ordinary builds and startup use the checked-in files.

Seeds run on an empty database. Upgrading an existing stack does not rewrite old player
identities, team countries, earned scores or purchased gift snapshots. To adopt the new catalogue
in an old test database, explicitly run `scripts/demo.sh --reset` (this clears all gameplay data).

## Full demo (about three minutes)

```sh
scripts/demo.sh
# Explicitly clear this demo's data and start a fresh round:
scripts/demo.sh --reset
# Short smoke check that leaves the simulator running:
scripts/demo.sh --core --reset
```

The script uses bundled curl/jq inside the app container. It checks onboarding/rules, auto-pick,
team creation, REST/SSE scores, a substitution with 60 real seconds of pending state, late goals,
settlement, RP awards, gift purchase and an identical retry without a second debit.
Use a fresh round for the full flow; `--reset` explicitly clears existing teams, scores, rewards
and purchases. Reset is local-only. Tests use disposable containers, not this Compose database.

## Authentication and common calls

For the new social screens and avatar fields, see [the frontend integration guide](docs/community-api.md).
It includes endpoints, filters, response fields and the distinction between simulated content and
working gameplay APIs. Existing users receive default avatars on upgrade; **no reset is needed**.

Seeded users: `alice` (Brazil), `bob` (France), `carol` (England), `dave` (Spain), `eve` (Argentina),
`frank` (Germany) have home countries; `grace` and
`henry` do not. Bob and Carol have seeded rival teams in Round 1. No phone/OTP/real identity
provider is needed. Mock auth/dev endpoints are disabled outside `local`; application access
outside that profile is denied until real auth is implemented.

```sh
curl -H 'X-Dev-User: alice' http://localhost:8080/api/v1/me
curl -H 'X-Dev-User: alice' http://localhost:8080/api/v1/rounds
curl -c /tmp/sporty-cookies -X POST 'http://localhost:8080/api/v1/dev/login?username=alice'
curl -b /tmp/sporty-cookies http://localhost:8080/api/v1/rewards/wallet
```

Replace `ROUND_ID`, `TEAM_ID` and `GIFT_ID` with IDs returned by the API:

```sh
curl -H 'X-Dev-User: alice' -H 'Content-Type: application/json' \
  -d '{"preferHomeHero":true}' http://localhost:8080/api/v1/rounds/ROUND_ID/auto-pick
curl -N -H 'X-Dev-User: alice' http://localhost:8080/api/v1/rounds/ROUND_ID/stream
curl -X POST -H 'X-Dev-User: alice' http://localhost:8080/api/v1/dev/simulator/stop
curl -X POST -H 'X-Dev-User: alice' http://localhost:8080/api/v1/dev/rounds/ROUND_ID/settle
curl -H 'X-Dev-User: alice' http://localhost:8080/api/v1/rounds/ROUND_ID/result
curl -H 'X-Dev-User: alice' http://localhost:8080/api/v1/gifts
curl -X POST -H 'X-Dev-User: alice' -H 'Idempotency-Key: my-gift-1' \
  http://localhost:8080/api/v1/gifts/GIFT_ID/purchases
```

`Idempotency-Key` is required for team creation, substitution and purchase. The same request/key
returns the saved successful response even after state changes. Use current `expectedVersion`
for lineup edits/substitutions; 409 `VERSION_CONFLICT` means reload your team and review the action.
A successful substitution response includes `pendingSubstitution.effectiveAt`; before this time
the outgoing player still scores. It disappears when active. The captain is never reassigned.

## Rules and finality

- Five starters, five countries, one bench; free formation, no player credits.
- Appearance +1, goal +5, assist +3, yellow −1, red −3; own goal 0.
- Goals at minute **75 or later** double base points. Captain ×2 applies after that multiplier.
- Home Hero: active starter matching the team's saved home country gets **+2 per goal/assist**,
  outside both multipliers. A home captain's late goal is 5×2×2+2 = **22 points**.
- One substitution per round, effective **60 real seconds** after acceptance.
- Completed round: **50 RP** per participant, **100 extra RP** for every rank-1 team, including
  ties and solo entrants. Fantasy score and spendable RP are separate balances.
- Settlement freezes scores and awards RP in one transaction. Pending substitutions or an
  actively running simulator block settlement. No corrections/reopening after settlement.
- Gifts: **Matchday Coffee** (50 RP), **Football Store Discount** (100 RP), **Club Scarf** (150 RP).
  Categories are FOOD/SHOPPING/MERCH; purchases issue `SST-...` codes. Redemption is simulated:
  no merchant is connected and no physical gift is shipped.

## Events and live integration

POST `/api/v1/internal/match-events` with the configured `X-Provider-Token` (demo provider
`simulator`, default token `local-demo-provider-token`):

```json
{
  "provider": "simulator",
  "providerEventId": "manual-goal-1",
  "revision": 1,
  "fixtureId": "<fixture UUID from player response>",
  "playerId": "<player UUID>",
  "eventType": "GOAL",
  "matchMinute": 75,
  "occurredAt": "<UTC time between LIVE deadline and now>",
  "voided": false
}
```

200 means the transaction committed. Exact duplicates return original acceptance; changed payload
with the same revision is rejected. Higher revisions replace prior events; `voided:true` cancels
one. Older revisions are stored without rescoring. Occurrence time selects the active lineup;
football minute selects the late-goal multiplier. The simulator compresses each match minute to
two real seconds, includes duplicates/corrections/delayed events, and resumes from stored events
when explicitly started after a restart. It is stopped by default on app restart.

SSE sends named `ROUND_SNAPSHOT` events every two seconds with `stateVersion`, `asOf`, round,
`myTeam`, top-100 global `leaderboard`, and own `result` when settled. Replace state rather than
adding deltas. For equal versions accept newer `asOf` (pending substitutions can activate without
a database mutation). Reconnect immediately sends current state; no Last-Event-ID replay.
On settlement refresh `/rewards/wallet`; purchases use REST responses. All private team/result/
purchase data is owner-scoped. REST pagination uses `items/page/size/total`; leaderboard wraps
its page in `standings`.

Frontend: proxy `/api` to the backend, preserve cookies and disable SSE buffering. This supports
native EventSource after `/dev/login`. For LAN sharing use the host's LAN IP on port 8080; keep
the database private. There is no direct cross-origin configuration in the default build.

The generated [OpenAPI snapshot](docs/openapi.json) describes implemented endpoints; controller/
DTO code is authoritative. Refresh from a running build:

```sh
docker compose exec -T app curl -fsS http://localhost:8080/v3/api-docs > docs/openapi.json
```

## Development and verification

JDK 21+ and Docker are needed to run tests outside Compose. Maven is downloaded by the wrapper.

```sh
./mvnw verify
docker compose -f compose.yaml -f compose.dev.yaml up -d postgres
./mvnw spring-boot:run -Dspring-boot.run.profiles=local
```

The optional development override exposes PostgreSQL on `127.0.0.1:5432` only. On macOS if
Testcontainers cannot find the socket, use `DOCKER_HOST=unix://$HOME/.docker/run/docker.sock`.
The repository's Maven settings intentionally avoid machine-specific corporate repositories.
Dependencies are pinned to Spring Boot 4.0.9 and compatible springdoc 3.0.3.

Tests cover scoring combinations and boundaries, authentication, idempotency, corrections,
substitution intervals, optimistic conflicts, final settlement, RP crediting, concurrent purchases,
injected transaction failures, SSE ownership and simulator replay. Implementation status and
acceptance evidence are tracked in [PLAN.md](PLAN.md).

Verified on 2026-10-29: **112 passing automated checks**, including all 60 publicly accessible
player portraits, avatars, social-content APIs and viewer-specific filters. The complete Compose scenario covers gift purchase;
the earlier 2026-10-27 check also confirmed persistence of results, wallet and purchases and SSE
reconnection across an app restart.

Real football identities and locally hosted photos make the catalogue realistic; fixtures and
results are simulated, as is gift fulfilment. Leagues, rivalries, Banter and manager discovery now
have read-only APIs with simulated content; join/rematch/reactions/backing transactions and a
fan-points wallet are not implemented. Missions and notifications (alerts about round starts,
scoring events or substitutions), frontend implementation, live sports/auth/partner integrations,
Kafka, Redis and multi-instance delivery remain outside the current backend scope.
